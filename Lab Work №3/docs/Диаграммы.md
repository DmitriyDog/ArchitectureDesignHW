#### 1. Принцип KISS (Keep It Simple, Stupid)
Код должен быть максимально простым и очевидным. Не нужно усложнять там, где можно обойтись простым решением.  

Пояснение: Метод process_purchase написан линейно, без вложенных условий и сложных конструкций. Каждый шаг логики покупки очевиден: проверил игрока → проверил товар → проверил наличие → списал деньги → выдал предмет.
```py
class PurchaseHandler:
    def process_purchase(self, request: PurchaseRequest) -> PurchaseResponse:
        # KISS: простая, линейная логика без лишних абстракций
        # Каждый шаг понятен и читается сверху вниз
        
        # 1. Проверяем игрока
        player = self.player_repo.get_player(request.player_id)
        if not player:
            return PurchaseResponse(success=False, message="Player not found")
        
        # 2. Проверяем товар
        shop_item = self.product_repo.get_shop_item(request.shop_item_id)
        if not shop_item:
            return PurchaseResponse(success=False, message="Item not found")
        
        # 3. Проверяем наличие
        if shop_item.quantity_available < request.quantity:
            return PurchaseResponse(success=False, message="Not enough stock")
        
        # 4. Платим
        payment_result = self.payment_client.charge(
            request.player_id, 
            shop_item.price * request.quantity
        )
        if not payment_result.success:
            return PurchaseResponse(success=False, message="Payment failed")
        
        # 5. Выдаем предмет
        self.inventory_client.add_item(request.player_id, shop_item.item_id)
        
        return PurchaseResponse(success=True, message="Purchase completed")
```

#### 2. Принцип YAGNI (You Aren't Gonna Need It)
Не нужно добавлять функциональность "на всякий случай". Только то, что реально нужно сейчас.  

Пояснение: Репозиторий содержит только те методы, которые действительно вызываются из сервисов. Нет "заготовок" на будущее, нет методов для массового обновления цен или сложной фильтрации, потому что сейчас это не требуется.
```py
class ProductRepository:
    def __init__(self, db_connection):
        self.db = db_connection
    
    # YAGNI: добавляем ТОЛЬКО те методы, которые реально используются
    # Нет методов update_product(), delete_product(), get_product_by_type() и т.д.
    
    def get_shop_item(self, shop_item_id: int) -> Optional[ShopItem]:
        """Реально используется в purchase_service"""
        for item in self.db.get("shop_items", []):
            if item.id == shop_item_id:
                return item
        return None
    
    def update_quantity(self, shop_item_id: int, quantity: int) -> bool:
        """Реально используется после покупки для уменьшения остатка"""
        # простая реализация
        pass
    
    # НЕТ методов, которые не используются:
    # - get_all_items_with_filters() - не нужно
    # - bulk_update_prices() - не нужно
    # - apply_seasonal_discount() - не нужно
```

#### 3. Принцип DRY (Don't Repeat Yourself)
Не дублировать код. Каждая часть знания должна иметь единственное представление в системе.  
Пояснение: Логика проверки доступа игрока вынесена в отдельный класс ValidationService.

```py
class ValidationService:
    # DRY: единое место для проверки прав игрока
    @staticmethod
    def validate_player_access(player_repo, player_id: int, item_player_id: int) -> bool:
        """Проверка, что игрок имеет доступ к предмету"""
        if player_id != item_player_id:
            return False
        player = player_repo.get_player(player_id)
        return player is not None
```

```py
class InventoryRepository:
    def get_inventory_item(self, player_id: int, item_id: int):
        # Используем общую валидацию вместо дублирования кода
        if not ValidationService.validate_player_access(self.player_repo, player_id, item_id):
            return None
        # ... остальная логика
```

```py
class PurchaseHandler:

            request.player_id, 
            request.player_id
        ):
            return PurchaseResponse(success=False, message="Invalid player")

#### 4. SOLID - Single Responsibility Principle (Принцип единственной ответственности)
У класса должна быть только одна причина для изменения.
Пояснение: Каждый класс имеет четко определенную зону ответственности. PlayerRepository не знает об инвентаре, PurchaseHandler не занимается отправкой email-уведомлений, PaymentClient не имеет методов для работы с БД.

        pass

        pass
    
    # Нет методов для работы с инвентарем или платежами
```

#### 5. SOLID - Open/Closed Principle (Принцип открытости/закрытости)
Классы должны быть открыты для расширения, но закрыты для изменения.
Пояснение: Класс PurchaseHandler закрыт для изменения — он не требует правок при добавлении новой платежной системы. Но открыт для расширения — мы можем передать любую реализацию PaymentClientInterface.

```py
from abc import ABC, abstractmethod

class PaymentClientInterface(ABC):
    """Абстракция, закрытая для изменения"""
    @abstractmethod
    def charge(self, player_id: int, amount: float) -> dict:
        pass

# Реализации открыты для расширения
class StripePaymentClient(PaymentClientInterface):
    """Можно добавить новую платежную систему без изменения существующего кода"""
    def charge(self, player_id: int, amount: float) -> dict:
        # Специфичная логика для Stripe
        return {"success": True, "transaction_id": "stripe_123"}

class PayPalPaymentClient(PaymentClientInterface):
    """Еще одна реализация - расширение, а не изменение"""
    def charge(self, player_id: int, amount: float) -> dict:
        # Специфичная логика для PayPal
        return {"success": True, "transaction_id": "paypal_456"}
```
